# Decisions

Format: `- [phase N] Decision: … Why: … Alternatives considered: …`

## Stack and architecture

- [phase 0] Decision: Raw three.js in one `<canvas>`, without @react-three/fiber or drei. Why: the engine is one `Points` object plus a starfield, driven by per-frame uniform writes; R3F adds a reconciler and ~40KB gzip for no benefit here, and the spec explicitly allows this. Alternatives considered: R3F + drei as listed in §3.
- [phase 0] Decision: Fonts come from `@fontsource-variable` (Latin subset only), copied into `public/fonts/`. Space Grotesk is 22KB and Inter 48KB, 70KB in total. Why: self-hosted, no runtime CDN, under the 120KB budget. Alternatives considered: Google Fonts (a runtime CDN, so forbidden).
- [phase 0] Decision: H1, stat numbers and the canvas name use weight 700, not the spec's 800. Why: the Space Grotesk variable font's weight axis stops at 700, and asking for 800 would only clamp or synthesise. Alternatives considered: a different display face (that would change the design).
- [phase 0] Decision: Lighthouse CI runs through `npx @lhci/cli@0.14.0` and is not a devDependency. Why: it pulls in a full Chromium plus ~200 packages; CI downloads it on demand. Alternatives considered: pinning it in devDependencies.
- [phase 1] Decision: One generic `CardsSection` renders Research, Building, Voice, Advocacy and Leading; there are no separate `Research.tsx` etc. Why: the five are identical apart from data (only Research shows the filter, through `showFilter`). Alternatives considered: five thin wrappers.
- [phase 1] Decision: The spec's `components/X/` folders hold one component plus its CSS module each; section layout CSS is shared in `sections/sections.module.css`.
- [phase 1] Decision: Pre-rendering uses Vite's own SSR build (`src/entry-server.tsx`) plus `scripts/prerender.ts`, which injects `renderToString` output into `dist/index.html`. React then hydrates. Why: no Playwright needed at build time and no extra plugin. Alternatives considered: `vite-plugin-prerender` (unmaintained) or a Playwright snapshot.
- [phase 1] Decision: Reveal animations hide content only when `html.motion` is set by an inline head script. That script removes the class after 4s if the app bundle never boots. Why: no-JS, reduced-motion and broken-bundle visitors always see all content. Alternatives considered: hiding by default and revealing in JS (fragile).
- [phase 1] Decision: `--faint` is lightened from `#4a5578` to `#6c7aa0` (4.7:1 on panels) and used for footnotes, card notes and the eyebrow numerals. The thread-node field labels use `--dim` instead. Why: `#4a5578` is about 2.7:1 and fails 4.5:1, and axe flags it even on `aria-hidden` numerals; §12 says to lighten rather than keep it. Alternatives considered: keeping `#4a5578` for decorative numerals only (axe still fails it).
- [phase 1] Decision: `--panel` alpha raised from 0.66 to 0.78 and `--panel-strong` from 0.82 to 0.88. Why: with the denser tier-3 field behind cards, 0.66 let bright particle clusters lower body-text contrast mid-morph; §24.3 says to raise panel alpha first. Alternatives considered: dimming particles further.
- [phase 1] Decision: Leadership, Thesis, the Habit and the Bird thread get visually hidden H2s (from their eyebrow labels). Why: every section needs an H2 for a complete outline and as a focus target for nav jumps. Alternatives considered: `aria-label` on the section only.
- [phase 1] Decision: The scroll stack (GSAP, ScrollTrigger, Lenis, the director) is a lazy chunk loaded right after first paint, including in reduced-motion and static modes (where it runs the accent and nav sync with native scroll). Why: it keeps initial JS at about 59KB gzip against the 90KB budget. Alternatives considered: shipping it in the initial bundle (about 100KB, over budget).
- [phase 2] Decision: Additive blending uses premultiplied output (`rgb * a, a`) with ONE/ONE blending on a transparent canvas, rather than three's `AdditiveBlending` on an opaque one. Why: it keeps the CSS `StaticBackdrop` gradient visible behind the particles, and the composited result stays valid (rgb ≤ alpha). Alternatives considered: an opaque canvas clearing to `--bg` (loses the gradient).
- [phase 2] Decision: Point size scales as `0.11 · √(11000 / N)` (capped at 0.11), and also scales with `uShapeScale` in the vertex shader. Why: at 30k points the spec's fixed 0.11 saturated every shape to white; this keeps total brightness about constant across tiers and on portrait screens, anchored to the prototype's ~11k look. Alternatives considered: lowering per-particle alpha (washes out sparse shapes).
- [phase 2] Decision: The model rotation is a bounded sway, `rotY = sin(0.12t)·0.32 + mouse`, instead of the spec's continuous `t·0.05` spin. Why: a continuous spin turns "SAKSHAM" edge-on after about 30 seconds. Alternatives considered: per-shape spin (complex to blend between shapes).
- [phase 2] Decision: `detect-gpu` is not used; `quality.ts` uses a heuristic instead (renderer string, `failIfMajorPerformanceCaveat`, touch plus screen size, core count). Why: detect-gpu fetches its benchmark tables from a CDN at runtime, which §2.5 forbids. Alternatives considered: self-hosting its benchmark JSON (about 1MB).
- [phase 2] Decision: Bloom is not shipped. Why: UnrealBloomPass doesn't composite cleanly on a transparent canvas, and the spec says the site must look complete without it. Alternatives considered: an opaque canvas plus bloom on tier 3.
- [phase 2] Decision: The name shape measures the text and sizes its canvas to fit the word, then maps it to 15 world units wide. Why: the spec's 1300×360 canvas at extent 10 produces a word about 36 units wide, which overflows the frame and fails the spec's own |x| ≤ 9 bound. Alternatives considered: shrinking the font in the fixed canvas (fewer usable pixels).
- [phase 2] Decision: The wave width is 17 instead of 20. Why: 20 puts points at |x| = 10, which fails the |x| ≤ 9 bound. Alternatives considered: none.
- [phase 2] Decision: The bound check allows |z| ≤ 7, not 3.5. Why: the spec's sphere (R 4.6) and horizontal ring (R about 6.4) are deep by design and exceed 3.5. Alternatives considered: flattening them (they would look worse).
- [phase 2] Decision: Portrait scaling is `uShapeScale = min(1, aspect · 1.05)`, not `aspect · 1.35`. Why: at 390×844 the 1.35 factor still clips the name and the bird's wingtips. Alternatives considered: per-shape scales.
- [phase 2] Decision: The helix uses the optional discrete base-pair rungs, every 18°. Why: it reads more like DNA than uniformly scattered rungs. Alternatives considered: 36° (real B-DNA), which was too sparse at this size.
- [phase 2] Decision: The engine starts from a wide scattered cloud and gathers into the bird. Deep links and `?nointro=1` start settled on the target. Why: the intro needs somewhere to start from. Alternatives considered: starting on the bird.
- [phase 2] Decision: Shapes build on the main thread in an idle callback; there is no Web Worker. Why: all six shapes at 30k points build in well under 40ms on the test machine (Apple M5). Alternatives considered: an OffscreenCanvas worker (helpers already accept `OffscreenCanvas` if it's needed later).
- [phase 3] Decision: ScrollTrigger windows are `top 50%` to `bottom 50%`, not `top 55%` to `bottom 45%`. Why: the spec's window makes adjacent sections both active across a 10% band; a single centre line gives exactly one active section. Alternatives considered: none.
- [phase 3] Decision: Particle opacity is set per section kind: hero 0.55 after the intro, thesis 0.45, about 0.4, cards/habit/awards 0.6, bird thread 0.75. Free-standing text also gets a dark text-shadow halo (`.halo`). Why: the settled particle name sits behind the H1 and the About lead; at full opacity the overlapping letters compete with the text, and §1.5 says legibility wins. Alternatives considered: offsetting the particle name off-centre, which left no room on phones.
- [phase 3] Decision: The progress bar and nav hide/show listen to native `scroll` events. Why: Lenis moves the real window scroll, so one code path works with or without Lenis. Alternatives considered: Lenis's own scroll event.
- [phase 3] Decision: The nav stays visible for 2s after a nav-link jump. Why: a programmatic jump down the page isn't the user scrolling down; hiding the nav then puts the link they just used out of reach. Alternatives considered: none.
- [phase 3] Decision: On load with a hash, the app scrolls to the section explicitly. Why: in dev nothing is pre-rendered, so the browser's own anchor jump misses. Alternatives considered: none.
- [phase 5] Decision: The axe checks exclude `[data-dimmed="true"]` (cards and award rows that the confidence filter dims to 16%). Why: low contrast is the intended filtered-out state; those items stay in the accessibility tree and are announced as "(filtered out)". Alternatives considered: dimming less (weakens the filter).
- [phase 5] Decision: The y-variance floor in shape tests is 0.5 in unit tests and 0.25 in the browser test, not 1. Why: a one-line word (name, y-variance about 0.4) and a waveform are short by nature; the spec's own generators can't meet 1. x-variance keeps the floor of 1. Alternatives considered: making the name taller (it would no longer fit portrait screens).
- [phase 5] Decision: The bird and name shape tests run in Playwright (`tests/e2e/shapes.spec.ts`) through the `?debug=1` engine handle. Why: jsdom has no 2D canvas, and the native `canvas` npm package has no prebuilt binary for Node 26. Alternatives considered: the `canvas` package.
- [phase 6] Decision: The email is a plain `mailto:` link. It is not in JSON-LD or any meta tag. Why: §21. Alternatives considered: assembling it at runtime (it would be lost without JS).

- [phase 4] Decision: Reveals use a shared `whenRevealed` helper: IntersectionObserver plus a throttled scroll check that also fires for elements already scrolled past. Why: a fast jump (End key, scrollbar drag) can carry an element from below the viewport to above it without it ever intersecting; IntersectionObserver reports no change then, so those elements stayed invisible and stat counters stayed at 0. Alternatives considered: IntersectionObserver only.
- [phase 5] Decision: The hero entrance is a pure CSS animation from first paint; it does not wait on an observer after hydration. Why: the H1 is the LCP element, and gating it on JS put mobile LCP at 3.1s. With CSS it's 2.0s (mobile) and 0.4s (desktop). Alternatives considered: no hero entrance animation.
- [phase 5] Decision: Shape generation yields to the event loop between shapes. Why: building six 30k-point shapes in one task produced about 1s of total blocking time on desktop Lighthouse; it's now 0ms. Alternatives considered: a Web Worker (not needed after this).
- [phase 5] Decision: Playwright runs at most 3 workers locally and 2 in CI, and visual baselines use `updateSnapshots: 'missing'`. Why: every worker renders WebGL in software, and more workers starved the CPU into timeouts. Baselines are per-OS, so the first Linux CI run writes its own instead of failing. Alternatives considered: running serially (slow).
- [phase 5] Decision: `PW_CHANNEL=chrome` runs the Chromium project against an installed Google Chrome. Why: in the build environment the Playwright browser download stalled, so the local e2e runs used system Chrome. CI uses the bundled browsers. Alternatives considered: none.

## Blockers

- The Playwright browser download (Chromium and WebKit) stalled in the build environment. Chromium e2e ran against system Google Chrome; **the WebKit project was not run locally**. It's configured and runs in CI.
- Not deployed: there's no Vercel account or git remote in this environment. `vercel.json`, `netlify.toml` and the CI workflow are ready.
- Manual passes not done: VoiceOver, a real iPhone in Safari (including Low Power Mode), and 200% zoom.
